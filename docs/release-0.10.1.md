这是 0.10.0 之后的第一个末位版本，库结构仍是 schema v20，不需要迁移。从这一版起，每次替换本机安装都换新版本号，流程见[本地发版与替换](local-release.md)。

## 为什么要有 `desktop:install`

0.10.0 之后到本版之间，本机替换了 9 次，靠的都是手工步骤，版本号一直停在 0.10.0。只靠状态栏里的提交标识分辨新旧，很容易看错。

还有一次替换赶上了流水线修订轮刚刚开始：停止接口返回了 409，手工发了 SIGTERM，结果那一轮在开始约 40 秒时被取消，只能手动恢复。

安装脚本把这两件事都卡住：
- 版本号没变的构建，拒绝安装。
- 后台有活动任务时，拒绝替换。
- 停止接口被拒时，重新打开应用后中止，绝不直接杀进程。

  - 服务端从输出目录收回 5 张完整的图交给复盘。以前这种情况整轮作废。

## 本机替换

2026-10-13 00:03，在提交 `57a2eeb` 的干净构建上执行 `npm run desktop:install`，0.10.0 → 0.10.1：

- **替换前**：第一次查状态时，后台有 1 个活动任务——一条议题上的单轮讨论在等 Agent 回复。按规则等它跑完（约 4 分钟），`activeTasks` 回到 0 后才执行替换。
- **退出与停止**：应用退出，服务正常停止；全程没有直接杀进程，也没有任务被打断。
- **备份**：旧应用打包为 `app-backups/Council-0.10.0-20261013-000339.app.zip`（约 48 MB）。
- **替换**：两个可执行文件与构建产物逐字节一致，`Info.plist` 版本为 0.10.1，前端构建标识带 `57a2eeb`。
- **重启核对**：服务就绪，schema v20，日志库身份没变；议题 85、消息 2182、决策 180、任务 645，与替换前一致。

## 限制

- 「卡住判定」在真实数据上还没有被触发过。第 3 轮没有卡住，所以目前只由 E2E 替身验证。
- 服务停止或重启打断委派时，界面显示的是「任务执行已取消」，容易误认为是用户手动取消的。这个问题单独跟进；装了 `desktop:install` 之后，替换时有任务在跑会被拒绝，正常发版不会再遇到。
- 浏览器验收用的是 Agent 替身，不代表真实上游模型已经验收。
