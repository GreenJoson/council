# 执行交付与恢复

Council 将完成条件、执行证据、待处理事项和失败恢复接在现有议题与实施项上。普通讨论保持只读；只有显式委派才进入已授权的隔离执行流程。

## 完成条件

在任务卡选择执行者、审核者与写入权限后，填写验收标准并选择完成策略。批量委派使用同一策略，每项标准取自己的任务详情，没有详情时取标题。

| 策略 | 审核通过后的任务状态 | 适用方式 |
|---|---|---|
| 人工验收后完成（新委派默认） | 保持进行中，显示待人工验收 | 用户在任务状态中填写本次验收证据，再选完成 |
| Agent 审核通过即完成 | 自动完成，记录审核结论与提交 | 用户明确允许自动完成的任务 |

标准和策略在创建委派时冻结，进入实施指令、执行和复审上下文。Agent 审核通过只代表它的检查结果；人工策略要求 Human 新提交非空验收依据，不能沿用已有 Agent 摘要。Node、Rust 写入接口和 SQLite 触发器共同约束这一边界，并继续使用任务版本号拒绝过期写入。执行期间用户更新任务后，Agent 的成功与失败结果都不能覆盖这次人工更新。用户自行完成外部工作后，也可提供依据完成任务，无需重新调用 Agent。

旧委派迁移为“审核即完成”，不追改已完成状态；旧记录没有验收标准时保持空白。

## 执行权限与登录

Agent 设置中的权限是上限；每条委派在创建时另行记录本次权限。提高 Agent 上限不会自动提高旧任务的权限。任务卡显示实际权限；接续默认保留原权限，若 Agent 上限允许，可在“接续执行权限”显式选择“完全控制”。服务验证当前上限后创建新运行，保留原记录并审计前后权限；权限变化后重新生成实施指令。

Claude 的“工作区写入”使用 `acceptEdits`，Bash 等操作仍可能需要批准；“完全控制”使用 CLI 的跳过审批模式，但仍须遵守任务范围和验收标准。普通讨论及审核继续只读。

操作权限不等于账号认证。最终 OAuth 过期或 401 会归类为认证失败，即使本次运行早先出现过工具审批拒绝。先在终端运行 `claude auth login`，完成登录后再显式接续；增大执行权限不能修复过期登录。历史失败记录保留当时的分类，不追改旧审计。

## 执行记录

当前调用、历史调用和任务委派中提供“查看执行记录”，按需读取持久化的分页事件。委派保留创建条件、Agent/模型与配置修订、有效权限、执行轮次、阶段摘要、提交、审核及失败事件。恢复生成新记录，并关联旧委派，历史入口继续可查。

普通运行只记录 Runtime 已发出的生命周期和工具事件。工具参数、私有草稿和原始会话不进入审计；公开字符串先脱敏。审计行禁止覆盖，议题删除时可级联删除，因此这是本机执行证据，并非独立的防篡改存证服务。

原生 CLI 委派持久化生成指令、执行验证、提交和审核阶段；从结构化事件记录实际回合数、工具调用计数及最近工具名，不保存工具参数、正文或推理。未提供的指标不补造。旧运行没有事件时显示明确空态。ACP 上下文占用不作为计费 Token，当前不展示推算费用；跨运行的完整工具证据检索仍属后续范围。

## 分阶段预算与持久检查点

Claude 的短讨论/实施指令继续使用 `COUNCIL_CLAUDE_MAX_TURNS`（桌面默认 24）。实施使用 `COUNCIL_CLAUDE_EXECUTION_MAX_TURNS`（默认 120），独立审核使用 `COUNCIL_CLAUDE_REVIEW_MAX_TURNS`（默认 48）。这些是每次 CLI 调用的上限，不是保证完成的次数；已有总超时、事件流和最终摘要限额继续生效。Codex 没有等价回合上限时不展示推算预算。

`error_max_turns`、调用预算耗尽和账号额度耗尽在任务卡显示为“已暂停，等待接续”，其他错误区分认证、模型、权限、瞬态和未知失败。持久状态仍为 `failed`，实施项受阻、队列停止；“暂停”是可恢复失败的界面语义，不代表进程还在运行。不会自动增加预算或重放写操作。额度耗尽要先等待恢复或调整账号，点击接续本身不会补充额度。

本地私有检查点在 CLI 初始化时保存会话 ID，执行过程中保存白名单进度。完成的实施指令和任务范围/验收标准/执行权限/Agent 配置指纹一并保存；显式接续时指纹一致则复用指令，变化则重新生成。跨 worktree 接续仍创建新模型会话，不将含旧工作目录的原会话直接复用；已有源代码、有效指令、最近执行摘要和独立审核意见用于交接。执行摘要标为模型自述，不能替代真实文件、验证结果或人工验收。检查点和原始会话 ID 不进入公开 DTO/审计，旧记录无检查点时不补造历史。

目前任务仍由桌面托管的 Node sidecar 执行；退出应用会停止服务，重启后保留记录并要求显式恢复。脱离桌面生命周期的常驻 Worker 尚未实现，这次没有引入 Go 服务或 PostgreSQL。

## 需要我处理

侧栏入口按当前项目汇总，并跳回原议题处理：待确认决策、待人工验收任务、阻断任务、最新圆桌留下的阻断分歧、执行失败，以及等待用户回复/确认的运行。

列表直接查询源状态，不另存一份可漂移的通知状态。实施项以最新委派为准，议题调用失败以最新运行为准，较新圆桌取代旧阻断终局；完成、确认或关闭后经现有同步机制更新。列表按议题合并，不提供跨项目提醒。

## 恢复与重新委派

“从已提交进度恢复”只适用于失败或取消、且已保存提交检查点的委派。恢复前检查任务版本、Agent 当前权限、受管目录、同一 Git 仓库、原 HEAD、基线祖先关系和原工作区干净状态。

检查通过后从已记录提交创建新的隔离分支、工作区和模型会话，先复审已有成果。审核要求修改时才继续执行。旧委派与旧工作区保留。恢复后的首次只读调用即使再次失败，新记录仍保留提交检查点。多个恢复请求同时到达时，只允许一个创建新的活动委派。

失败发生在提交前、但仍有受管工作区和原始基线时，可点击“接续未完成工作”。服务先验证原 HEAD 未变，再用临时索引为未提交的新增、修改、删除建立快照；原索引、文件和失败记录保留。配置、数据库、日志、备份、疑似凭据、二进制及符号链接会被拒绝，忽略文件不纳入快照。快照只带入新的隔离工作区，不生成交付提交；执行者继续补齐并测试后，才按原验收标准提交、审核和人工验收。再次中断仍可显式接续。

已保存交付提交且在执行/提交阶段中断时，可安全接回之后的修正草稿：HEAD 须匹配最近已记录提交，草稿仍走同一敏感路径和内容检查，只写入新工作区。旧版记录只要有这些阶段证据也可恢复。审核阶段出现来历不明的未提交改动、原 HEAD 被外部改变或原工作区不可验证时仍拒绝。没有未提交代码时，“重新委派”从项目当前基线开始。旧任务不会因升级自动重跑或变为完成。

委派的完整 Git 检查使用 `COUNCIL_DELEGATION_GIT_MAX_OUTPUT_CHARS`（默认 1,000,000 字符），独立于只读 diff 展示预算；超过检查预算会停止，不能跳过敏感内容扫描。草稿恢复的单文件字节数也保守使用此上限。

主动阶段交接使用 `COUNCIL_CHECKPOINT` 加 JSON 数组 `completed`、`validation`、`remaining`。执行者收到预算提示，长任务应提前保存文件、真实检查结果和下一步，再正常返回交接；服务保存摘要并显示可接续暂停，不提交、不审核、不自动重放写操作。格式不合法也不会当作完成。此协议依赖执行者主动遵守；硬超时、认证失败或进程被杀不能保证得到交接，但已有文件和最后一次成功保存的记录仍保留。

只读的任务说明/审核调用遇到已识别的瞬时错误时，按 `COUNCIL_ORCHESTRATION_DEFAULT_MAX_ATTEMPTS` 有界重试，间隔由 `COUNCIL_DELEGATION_RETRY_DELAY_MS` 配置（默认 1500 毫秒）。写入调用、认证失败、额度耗尽、模型不可用和不明错误不自动重放。服务重启将未终结委派标为中断，用户检查后选择恢复或重新委派。

## 数据与验证

schema v15 增加完成条件，v16 增加审计、失败分类与恢复来源，v17 为委派追加可空的私有检查点列。Node 仍是唯一迁移者，沿用 [迁移前备份、排他事务和失败回滚](schema-migration-safety.md)；Rust 等待 sidecar 就绪后验证 v17。旧二进制不兼容 v17，回退应用时应使用对应版本的迁移前备份，不能修改版本号伪装降级。

活动委派运行期间不能修改其 Agent/Provider 配置，也不能关闭议题；请先取消并等待进程停止。

隔离测试覆盖人工验收权限/CAS、审计分页与脱敏、待办消退、迁移故障回滚、修正中断后提交加草稿接续、来历不明的脏工作区拒绝恢复、敏感文件在暂存前拦截、并发恢复、大报告审核、阶段交接及写入不自动重放。浏览器通过真实 HTTP/SSE 与测试 Agent 替身检查交互；这不代表真实模型、安装包或生产项目已完成验收。

## 审核与交付边界

审核 diff 按文件分别读取，避免聚合总长先触发输出上限；单文件超限明确列为需补查。材料包含完整路径清单，先安排代码/测试，再安排配置和文档；每个文件分别分配节选预算。大 JSON 不再挤掉后面的源码。所有节选和未展示的文件标记为需补查，审核者在同一隔离工作区只读检查完整变更，通过 `inspectedFiles` 声明实际补查的路径。漏报必需路径的批准会转为审核受阻，不会直接交付。这是模型审核的覆盖声明，不是独立证明它理解了每一处代码；人工验收边界保持不变。

审核返回 `approved`、`changes_requested` 或 `blocked`。`changes_requested` 只用于已核实的实现问题；无法核对材料使用 `blocked`，保留提交并等待恢复审核，不再让执行者通过缩减实现或删除验收字段解决材料截断。修订轮次耗尽单独记录为 `review_revision_limit`，界面显示待接续、已有提交与最近审核问题。

每轮验证后的提交追加在上一份 Council 提交之上。Git 交付复用恢复的安全快照检查，确认路径、文本内容和文件类型后才更新真实索引；第二轮检查失败不会撤销上一份提交。阶段摘要先于提交持久化，提交成功即保存 SHA，之后审核失败仍能从提交恢复。提交不是审核通过，审核通过不是人工验收。

## 模块职责与后续边界

- `work-item-delegation-manager.ts`：任务权限/CAS、生命周期和执行审核次序。
- `delegation-runtime-stage.ts`：CLI 调用、阶段事件、进度、只读瞬态重试。
- `delegation-review.ts`：审核材料预算、完整清单、补查覆盖与结论协议。
- `delegation-execution-result.ts` / `delegation-handoff.ts`：主动阶段交接、历史摘要与审核意见传递。
- `delegation-git-delivery.ts` / `delegation-workspace-snapshot.ts`：安全扫描、追加提交与无损快照。
- `delegation-recovery.ts`：恢复工作区身份、HEAD、阶段证据与权限前置检查。
- `DelegationDeliveryEvidence.tsx`：从真实记录展示已有提交与审核问题，不推算完成比例。

当前仍由桌面进程托管执行。要支持关掉窗口后继续工作，下一步应引入独立 Worker、持久任务租约、心跳和退出/取消协议；不能仅把子进程设为 detached，否则重启与双实例可能重复写入。自动分段续跑也需要单独的累计预算、无进展检测和明确授权策略；本次不以无限重试替代这些边界。无须为了这些改动迁移 Go 或 PostgreSQL。
